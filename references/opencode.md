# 参考：opencode（已验证）

> 本文是 Delta 设计记录的正式文本。同步自 Qoder 记忆条目 `reference-opencode`（脚本 `tools/sync-from-memory.sh`，最近同步 2026-11-08）。


**opencode** is the agent the user decided to build delta around first (open source, multi-provider LLM, **native** ACP via `opencode acp`, subagent/role machinery) — see [project-delta](../laws/delta-reasoning.md). Docs: [permissions](https://opencode.ai/docs/permissions/), [ACP](https://opencode.ai/docs/acp/), [acp CLI](https://opencode.ai/v2/docs/cli/acp/) (`opencode acp` runs as a child process speaking newline-delimited JSON-RPC on stdin/stdout).

**The user's decisions (2026-11-08): delta writes its own permission engine — and then, in the follow-up, *"不再使用opencode权限，opencode权限好的部分我们抄过来就行"*, which removes their engine from the stack entirely.** So there is no double prompt to design around and no option of compiling our policy into their config; what survives is **copying the good parts of their semantics only**. Six worth copying, verbatim from its docs:

- *"Agent rules are appended after global rules; they do not replace the global array."* — layered, additive, never overriding. Under delta's ledger authorship invariant this is the shape of rule *evaluation*, not of delegation: appended terms may only narrow, and **the author of any grant row is always `human`** (AI may propose, never authorize) — see [project-group-decision-rules](../laws/group-decision-rules.md).
- *"A policy can hard-deny a permission check… It turns `allow` or `ask` into `deny` and never grants access."* — the human root ceiling already has a shape to follow.
- *"`external_directory` … is checked against `external_directory` before its `read` or `edit` rules."* — the path jail is a **pre-stage of rule evaluation**, not another pattern in the list. Changes our evaluation order.
- *"Every agent starts with this ordered base policy: `{ "action": "read", "resource": "*.env", "effect": "ask" }`"* — reads cannot truly be denied (see [project-delta](../laws/delta-reasoning.md): agents are ordinary processes), but sensitive reads become **ask**, which is the only enforceable read control at the ACP layer. Ship a default sensitivity list (.env, credentials, SSH, browser profiles).
- *"Allow always … Approve it and save the tool's proposed patterns for the project"* — persistent grants store **patterns**, not paths, so a ledger grant row should be `(actor, action, pattern, delegator, ttl, granted_by_human)`.
- Gated actions are `edit` / `shell` / `webfetch` (+ `read` via base policy), outcomes `allow|ask|deny`, matching is **glob with last-match-wins**, and there is *Ask once* / *Allow always* granularity.

**One thing explicitly NOT to copy**: *"The default policy allows `external_directory`, so external paths are not prompted unless you add a rule."* — its permissive default contradicts delta's "误杀优于静默" bias; record this so the argument "opencode does it that way" cannot be used later.

**Known gaps on their side**: nested subagent edit permissions are still an open request ([issue #13872](https://github.com/anomalyco/opencode/issues/13872)). Their rule expressiveness is capped by their glob language — no longer a design cost to us (we don't compile policy into their config; their engine is out of the stack), but it **is** the ceiling on what the agent's own internal tool-approval UI will do without asking us, which is the bypass surface recorded in [reference-acp](acp.md): ACP forbids calling host methods we don't advertise, and never obliges routing through them when we do. What we copy of their glob semantics should therefore be copied into **our** engine's vocabulary, so our `actor × action class × resource glob` triple and their internal behaviour at least agree on matching rules and last-match-wins.

## Its extensibility surface, checked when the user claimed *"OPENCODE 也没有方案"* (2026-11-08)

The claim is **half right, and the half that is right is the interesting part.** opencode does have two levers — but neither reaches below the tool layer, which is where [project-agent-compliance](../proposals/agent-compliance.md) puts the real boundary.

- **Custom tools** exist. Quote taken from the search snippet of the official page (the page itself would not fetch this session, so treat as **medium confidence, re-verify before citing in a design doc**): *"Custom tools are functions you create that the LLM can call during conversations"*, working *"alongside opencode's built-in tools like read, write, and bash"* ([docs](https://opencode.ai/docs/custom-tools/)). That is the discoverability answer, not the compliance answer.
- **Plugin hooks** exist and can intercept a tool call before it runs ([docs](https://opencode.ai/docs/plugins/)). The argument as a third party puts it: *"move enforceable rules into plugin hooks that block tool calls before they execute. The model can't 'forget' a hook"* ([nkapila](https://nkapila.me/posts/opencode-config)) — **third-party, unverified**. A reported ordering caveat circulating in the same community: *"Current OpenCode runs `tool.execute.before` first, then evaluates its permission rules against the final arguments"* ([reddit thread](https://www.reddit.com/r/opencodeCLI/comments/1vv1os2/one_config_line_kept_my_claude_code_command/)) — **unverified claim, do not state as fact**.
- **Why neither helps delta**: both sit *inside the agent*, and one permitted `bash` call can run an arbitrary program. The guard sees a tool invocation, not what the launched script did. That is the general ceiling, not an opencode omission — see [project-agent-compliance](../proposals/agent-compliance.md).
